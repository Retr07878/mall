## 附录 C：全链路验证到底在验证什么（方法论，W0 必读）

### C1. 一句话定义

**全链路验证 = 按用户真实使用顺序，把多个服务/中间件串起来跑一遍，并在每一步观察「HTTP 响应 + 数据库 + 缓存 + 消息队列」四层数据的变化，确认整条链路能协同工作、数据前后一致。**

它和"单接口测试"的区别：单接口只看返回值对不对；全链路看的是**数据在系统里怎么流动、事务怎么提交、异步怎么补偿**。

### C2. 为什么要做（5 个理由，都很实在）

| 理由 | 说明 | 今天真实例子 |
|---|---|---|
| 1. 环境验收 | 服务能启动 ≠ 能用 | 启动后才发现 MySQL 公钥、RabbitMQ 用户、购物车字段、优惠券 4 个坑 |
| 2. 建立系统观 | 看清 Controller → Service → Mapper → DB 的真实路径 | 下单不是"插一条订单"，而是 锁库存→插单→插明细→清购物车→发 MQ |
| 3. 建立基线 | 后面做秒杀/缓存优化要有"改造前"对照 | 现在下单是同步链路，lock_stock 无并发保护 → 你的靶子 |
| 4. 发现缺陷 | 能跑通不代表设计对 | `lockStock()` 查-改-写无锁、MQ 消息在事务内发送可能丢 |
| 5. 面试素材 | 「讲下你们下单流程」的答案就来自这里 | 你能说出 stock/lock_stock、状态机、延迟队列，比背八股值钱 |

### C3. 怎么做：三看 + 两轮

**三看（每个业务步骤都要做）**
1. **看响应**：HTTP code、业务 code、关键字段（token/orderId/payAmount）
2. **看数据库**：执行前后各查一次，做 before → after 对比（订单表、明细表、库存表、购物车表）
3. **看异步侧**：Redis（token 缓存）、RabbitMQ（延迟队列条数）、服务日志（有没有 ERROR）

**两轮**
- 第一轮：**正向链路**（happy path）—— 登录→搜索→加购→下单→支付，验证"正常能用"
- 第二轮：**异常/边界链路** —— 取消订单、库存不足、重复提交、不传券，验证"出错时数据不乱"
  - 举例：重复提交同一购物车 → 订单是否重复？库存是否多扣？
  - 举例：未支付取消 → lock_stock 是否释放、stock 是否没变

**记录方法**：每步记 4 行（请求 / 响应关键字段 / DB before-after / MQ 或 Redis 变化），见指南第五节表格。

### C4. 从这些信息里能看出什么（解读表）

| 你观察到的现象 | 能看出的设计/问题 |
|---|---|
| 下单后 `lock_stock+1`，`stock` 不变；支付后 `stock-1`、`lock_stock-1` | 项目采用「先锁库存、支付再扣减」模型：支持取消/超时回补，防超卖 |
| 下单后 RabbitMQ `mall.order.cancel.ttl` 多 1 条 | 超时取消靠**延迟队列**实现，不是定时扫表；30 分钟后转死信队列 → 消费者取消订单 |
| 登录后 Redis 出现 `mall:ums:member:test` | JWT 虽然无状态，但仍用 Redis 存 token 实现**登出/强制下线/续期** |
| 订单明细表里冗余了商品名、价格 | 订单是**快照**：商品后来改名/改价，订单详情不能变 |
| `pms_product` 有 stock，`pms_sku_stock` 也有 stock | SPU-SKU 模型：真实库存和价格挂在 SKU 上，下单扣 SKU 库存 |
| `lockStock()` 是「查出来 +1 + 写回」 | **并发不安全**：两个请求同时读 100，都写 101，超卖/少卖。这就是你 W1-W2 做秒杀要解决的靶子 |
| 生成订单方法上有 `@Transactional`，但 MQ 发送也在方法里 | **消息可能在事务提交前发出**：事务回滚了消息却发出去了 → 可靠性隐患（面试可讲"本地消息表/事务消息"方案） |
| 取消订单后订单 `status=4` | 订单状态机：0 待付款 / 1 待发货 / 2 已发货 / 3 已完成 / 4 已关闭；查代码确认每个状态由谁触发 |

### C5. 最有价值的产出：一张「问题清单」

全链路验证的真正产出不是"跑通了"，而是**跑通之后你能列出系统的问题**。例如本次可以列出：

1. `lockStock()` 读-改-写无并发保护 → 高并发超卖（→ 秒杀模块用 Redis+Lua 改造）
2. MQ 消息发送与事务边界不清晰 → 消息可靠性问题（→ 加重试/本地消息表）
3. 下单是同步链路，接口 RT 受 DB 影响 → 峰值性能差（→ MQ 异步化 + 压测数据对比）
4. 库存缓存一致性：DB 扣减后 Redis 无对应缓存方案（→ 缓存治理要考虑）
5. `lock_stock` 居然出现了负数（种子数据 98 号 SKU 是 -24）→ 说明历史数据/并发下确实可能出问题

**这张清单就是你后面设计文档（docs/design/）的输入**，也是面试时"你发现了什么问题、怎么解决"的答案。

### C6. 完成标准（怎么算"验证到位"）

- [ ] 正向链路每个步骤都有 请求→响应→DB before/after 记录
- [ ] 异常链路至少做了「取消订单」和「重复提交/库存不足」各 1 个
- [ ] 能用自己的话解释：stock vs lock_stock、状态机、延迟队列、token 为什么要存 Redis
- [ ] 能列出 ≥3 条系统问题（C5 那张清单）
- [ ] 把记录写进 `docs/study/00-我的验证记录.md`（含截图/命令输出）

### D1. MySQL（数据库）

| 方式 | 操作 |

### D2. Redis（Memurai）

| 方式 | 操作 |
|---|---|
| 单条命令 | `memurai-cli keys "mall:*"`、`memurai-cli get mall:ums:member:test` |
| 交互式 | 直接运行 `memurai-cli` 进入 `127.0.0.1:6379>`，敲 `keys *`、`type <key>`、`ttl <key>`、`get <key>`，`exit` 退出 |
| 实时观察 | `memurai-cli monitor`（能看到每次请求对 Redis 的操作，Ctrl+C 停止） |
| 图形化 | 可选装 RedisInsight / VS Code 的 Redis 插件（免费） |

关注点：登录后 `mall:ums:member:test`（token）、`mall:ums:resourceList:*`（权限资源缓存）、TTL 是否 7 天。

### D3. RabbitMQ（消息队列）

| 方式 | 操作 |
|---|---|
| 管理台（推荐） | 浏览器打开 http://localhost:15672 ，账号 **guest / guest** |
| 命令行 | `docker exec mall-rabbitmq rabbitmqctl list_queues -p /mall name messages` |

管理台看什么：
- **Queues** 标签 → `mall.order.cancel.ttl`（延迟队列，下单后应有 1 条 Ready）、`mall.order.cancel`（死信队列，30 分钟后才有消息）
- 点队列名进去 → 下方 **Get messages** 可以查看消息内容（注意 Get 会用 ack 方式取走，选 Reject 或 Nack 放回）
- **Exchanges** → mall 的交换机（`mall.order.cancel.ttl`、`mall.order.direct`）
- **Connections** → 能看到 mall-portal 的连接

### D4. 服务日志（第四处观察点）
