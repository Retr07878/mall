## 时序 1：后台登录 + JWT 鉴权（mall-admin / mall-security）

```mermaid
sequenceDiagram
    participant C as 前端
    participant S as Security 过滤器链
    participant U as UmsAdminService
    participant R as Redis
    participant J as JwtTokenUtil
    C->>S: POST /admin/login (username,password)
    S->>U: loadUserByUsername
    U-->>S: UserDetails + 权限
    S->>J: generateToken
    S->>R: 写入 token / 权限缓存
    S-->>C: {tokenHead, token}
    Note over C,S: 后续请求带 Authorization: Bearer xxx
    C->>S: GET /admin/info (Bearer)
    S->>J: parseToken / 校验签名
    S->>R: 查 token 是否存在（是否被登出）
    S->>S: DynamicAuthorizationManager 校验 URL 权限
    S-->>C: 数据
```

## 时序 2：下单主流程（mall-portal / OmsPortalOrderServiceImpl）

```mermaid
sequenceDiagram
    autonumber
    participant C as 前端
    participant Ctrl as OmsPortalOrderController
    participant O as OmsPortalOrderServiceImpl
    participant DB as MySQL
    participant MQ as RabbitMQ
    participant R as CancelOrderReceiver

    C->>Ctrl: POST /order/generateOrder (OrderParam)
    Ctrl->>O: generateOrder(orderParam)
    O->>O: 校验收货地址 memberReceiveAddressId / 获取当前会员
    O->>DB: cartItemService.listPromotion(memberId, cartIds) 查购物车+商品+SKU
    O->>O: 购物车项 → OmsOrderItem 快照（商品名/价格/数量/规格）
    O->>DB: hasStock() 校验库存（realStock = stock - lock_stock）
    O->>O: 优惠券/积分校验 + 金额分摊（handleCouponAmount / handleRealAmount）
    O->>DB: lockStock() 锁定库存（查-改-写 ⚠️缺陷1）
    O->>O: 计算 totalAmount / promotionAmount / couponAmount / payAmount
    O->>DB: insert oms_order（status=0 待付款，回填自增 id）
    O->>DB: insert oms_order_item（回填 order_id / order_sn）
    O->>DB: updateCouponStatus（优惠券标记已使用）
    O->>DB: updateIntegration（扣减会员积分）
    O->>DB: deleteCartItemList（购物车逻辑删除 delete_status=1）
    O->>MQ: sendDelayMessageCancelOrder（消息 TTL = normalOrderOvertime 分钟）
    MQ-->>MQ: TTL 到期 → 死信（mall.order.direct → mall.order.cancel）
    MQ->>R: CancelOrderReceiver.handle(orderId)
    R->>O: cancelOrder(orderId)
    O->>DB: status=4 / releaseSkuStockLock 释放锁定库存 / 回滚优惠券 / 返还积分
    O-->>Ctrl: {order, orderItemList}
    Ctrl-->>C: CommonResult(订单信息)

    Note over O,DB: ⚠️ 缺陷1：lockStock 是"查-改-写"，并发下丢失更新<br/>⚠️ 缺陷2：generateOrder 全程没有 @Transactional，失败不回滚<br/>⚠️ 缺陷3：hasStock 校验与 lockStock 锁定之间有时间窗（TOCTOU）
```

> 必答：`lockStock` 的并发问题是什么？延迟队列和定时扫表各自的优缺点？
> 答题要点：① 查-改-写三行非原子 → 两线程都读到 lock=0、都写 1 → 丢更新/超卖；修复用原子 UPDATE（带 `stock-lock_stock>=qty` 条件）或 Redis 预扣。② 延迟队列：实时性好、解耦，但消息可能丢/堆积、依赖 MQ 可用；定时扫表：简单可靠、补偿兜底，但延迟精度低（10 分钟粒度）、扫表压力大 —— 本项目 MQ 主用、定时任务兜底（`OrderTimeOutCancelTask` 的 @Component 默认被注释）。

## 时序 3：商品搜索（mall-search / EsProductServiceImpl）

```mermaid
sequenceDiagram
    participant C as 前端
    participant E as EsProductController
    participant S as EsProductServiceImpl
    participant ES as Elasticsearch
    participant DB as MySQL
    C->>E: GET /esProduct/search?keyword=
    E->>S: search(keyword, page)
    S->>ES: 查询（multi_match / filter / sort）
    ES-->>S: 命中商品 ID 列表
    S->>DB: 按 ID 回查商品详情（或直接返回 ES 文档）
    S-->>C: 分页结果
```
