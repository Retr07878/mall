# W1 任务清单：mall-security + Redis（阶段一）

> 目标：吃透 mall 的认证授权链路。W1 结束时能**白板画出过滤器链**并解释动态权限。
> 时间：周一~周四每天 3.5h 项目 + 周五~周日每天 5h 项目（共约 42h）

## Day 1（约 3.5h）：总览 + 启动链路

- [ ] 打开 `mall-security` 模块，把 14 个类按目录列一遍，分清：annotation / aspect / component / config / util
- [ ] 读 `SecurityConfig`：找出 `SecurityFilterChain` 里注册了哪些过滤器、哪些 URL 放行（`IgnoreUrlsConfig` 从哪读）
- [ ] **实验 1**：在 `JwtAuthenticationTokenFilter.doFilterInternal` 打断点，用 Swagger 调 `/admin/info`（带和不带 token 各一次），观察断点进出顺序
- [ ] 笔记：画出 `SecurityConfig → FilterChain` 结构图

## Day 2（约 4h）：JWT 签发与校验

- [ ] 读 `JwtTokenUtil`：签名算法、claim 里放了什么、过期时间怎么控制
- [ ] 读 `UmsAdminServiceImpl.login`（mall-admin 模块）：密码校验、token 生成、Redis 写入
- [ ] **实验 2**：登录后去 Redis 里找 token 的 key（`mall:ums:admin:admin`），手动删除它，再调 `/admin/info` 观察结果
- [ ] 回答（写进笔记）：
  - JWT 是无状态的，mall 为什么还要存 Redis？
  - 登出（logout）到底删了什么？改密码后旧 token 为什么失效？

## Day 3（约 4h）：动态权限

- [ ] 读 `DynamicSecurityMetadataSource`：如何把数据库里的 `ums_resource` 映射成 URL → 权限
- [ ] 读 `DynamicSecurityMetadataSource.getConfigAttribute` + `DynamicAuthorizationManager`：鉴权决策发生在哪一步
- [ ] 读 `RedisCacheAspect` + `CacheException`：资源缓存 key 怎么生成、何时失效
- [ ] **实验 3**：在数据库改一个角色的资源权限（或禁用某 URL），**不重启**刷新，验证权限立即生效
- [ ] 笔记：画 URL 权限判定流程图（请求 → 匹配资源 → 查角色 → 决策）

## Day 4（约 4h）：Redis 用法与总结

- [ ] 列出项目中 Redis 的 4 类用法：token、权限/资源缓存、验证码、首页/商品缓存（用 `grep -r "redisService"` 找调用点）
- [ ] 读 `RedisServiceImpl` + `BaseRedisConfig`：序列化方式、key 规范
- [ ] 写 W1 总结：**500 字**以内讲清「一次带 token 的后台请求，如何从过滤器走到 Controller」
- [ ] 自测：能不看代码说出 14 个类中每个的职责（说不出的标记出来补）

## 验收标准（周五复盘时自测）
