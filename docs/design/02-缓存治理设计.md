# 缓存治理设计文档（v1 模板）

> 用途：W0 定方案，W3 实现并填数据。重点讲清「你解决了什么问题 + 数据对比」。

## 1. 背景与目标

- 现状：mall 主要用单层 Redis 缓存（`RedisServiceImpl` / `RedisCacheAspect`），存在：
  - 缓存穿透（查询不存在的数据打穿到 DB）
  - 缓存击穿（热点 key 过期瞬间大量请求打到 DB）
  - 缓存雪崩（大量 key 同时过期）
  - 本地无缓存，热点数据每次都要走网络
- 目标（选目标接口：商品详情 `GET /product/detail/{id}`）：
  - P99 从 ~120ms 降到 <30ms
  - 缓存命中率 > 95%
  - 压测下 DB QPS 明显下降

## 2. 方案设计

| 问题 | 方案 | 说明 |
|---|---|---|
| 多级缓存 | Caffeine（本地）+ Redis（分布式） | 本地 TTL 短（如 30s），Redis TTL 长（如 10min） |
| 穿透 | 布隆过滤器 / 空值缓存 | 商品 ID 预热进布隆过滤器；空结果缓存 60s |
| 击穿 | 逻辑过期 + 互斥锁 | 热点 key 不设物理过期，异步刷新；或 Redis SETNX 互斥 |
| 雪崩 | TTL 加随机值（±20%） | 避免同一时刻集中过期 |
| 一致性 | 更新商品 → 删 Redis → 延迟 500ms 再删（延迟双删） | 也讨论 Canal 订阅 binlog 方案 |

## 6. 风险与兜底

- 本地缓存不一致：缩短本地 TTL + 更新时广播（可提 Caffeine 的 invalidate 方案）
- Redis 不可用：本地缓存兜底 + 限流保护 DB
- 布隆过滤器误判：可接受（漏判少量真实请求），不可出现误放行（必须保证不存在的一定被拦）
